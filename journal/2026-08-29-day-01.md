## 공부한 것

- HTML은 `main` 안에 소개 영역(`section.hero`), 기능 설명(`section.features`), 입력·결과 체험 영역(`section.demo`)을 순서대로 배치해 화면의 뼈대를 만든다.
- CSS는 `:root`의 색상 변수, Grid 레이아웃, 그리고 `@media (max-width: 760px)` 규칙으로 디자인과 모바일 화면을 담당한다.
- JavaScript는 입력 요소를 `getElementById()`로 가져오고, 버튼의 `click` Event에서 선택값을 읽어 추천 카드 3개를 만들어 화면에 넣는다.
- 현재 위치·날씨·추천 결과는 이미 화면에 있지만, 장소·이동 시간·날씨는 아직 실제 API가 아닌 예시 데이터다.
- 실행 확인: 서울숲역 → 성수역, 60분, 비, 카페 선택 시 실내 카페 TOP 3가 표시됐다.

## 구현한 것

- `detour-landing.html`의 단일 추천 문장을 TOP 3 추천 카드로 확장했다.
- 사용자가 남은 시간과 활동을 선택하고 버튼을 누르면, 선택 조합에 맞는 카드 3개가 표시된다.
- 각 카드는 순위, Match 점수, 예상 시간·비용, 추천 이유를 보여준다.
- JavaScript 문법과 변경 사항을 검사했다.
- 강사 피드백 안내 영역을 삭제하고, 현재 위치·도착 위치·날씨 입력을 추가했다.
- 비가 오는 날에는 실내 장소를 우선으로 보여주는 임시 추천 데이터를 추가했다.
- 실제 위치 기반 이동 시간은 지도 API를 연결하는 다음 단계에서 계산하기로 했다.

## 고민과 선택

- 2026-08-29 14:03 KST — 날씨를 추천 조건에 반영하는 아이디어를 추가했다. 맑음·비 등의 상황에 따라 실내/실외 장소의 적합도를 조정한다.
- 2026-08-29 14:03 KST — 현재 위치를 활용해 후보 장소까지의 예상 이동 시간과 목적지 방향 적합도를 계산하는 아이디어를 추가했다. 위치 권한을 거부한 사용자를 위해 출발지 직접 입력도 유지한다.
- 결정: 두 기능은 기본 추천 흐름을 완성한 뒤 Week 5의 지도·모바일 UX 단계에서 통합 가능성을 검토한다.
- 2026-08-29 14:08 KST — 핫플·혼잡도 데이터의 후보를 조사했다. 장소 검색과 좌표·거리·경로는 카카오 로컬/경로 API를 우선 검토하고, 서울의 주요 핫스팟 혼잡도는 서울시 실시간 도시데이터 API를 검토한다.
- 결정: 인스타그램은 임의의 장소·해시태그 데이터를 안정적으로 가져오는 주 데이터 출처로 사용하지 않는다. 초기 장소 후보를 사람이 선별할 때만 참고하고, 서비스 데이터는 공식 API 또는 직접 관리하는 데이터셋을 사용한다.
- 주의: 서울시 혼잡도는 특정 카페의 빈자리 정보가 아니라 주요 지역 단위의 인구 혼잡도다. 추천 문구도 “이 지역은 현재 붐비는 편”처럼 표현한다.
- 2026-08-29 14:41 KST — 강사 안내와 90분 수업 목표를 기준으로, 이번 세션은 실제 API/LLM 연결보다 더미 데이터 기반 프로토타입을 완성하기로 확정했다.
- 결정 근거: LLM은 신뢰할 수 있는 장소·날씨·경로 원천 데이터가 아니며, 카카오 REST API는 key 보안과 FastAPI 서버 준비가 필요하다. 둘 다 이번 세션의 핵심 성공 조건(입력 → 결과 카드)을 늦출 수 있다.
- 다음 주: FastAPI 환경에서 API key를 안전하게 관리하며 카카오 지도/장소 API 등 실제 데이터 연동을 검토한다.
- 2026-08-29 14:45 KST — 운영 원칙을 바로잡았다. 수업 지시나 새 아이디어가 생겨도 5주 MVP 범위와 주차 순서를 즉시 바꾸지 않는다. 새 기능은 핵심 경험 필요성, 현재 주차 필요성, 기술 구조 적합성, 일정 위험을 검토해 확장 기능으로 분리한다.
