## 4 · 장소 데이터 구조 정리와 결과 카드


- 주제: 장소 데이터 구조 정리와 결과 카드 정직하게 만들기
- 오늘의 목표: `index.html`의 장소 데이터 필드를 Week 3·4까지 이어질 이름으로 정하고, 카드가 보여주는 숫자를 입력 조건과 일치시킨다.

### 오늘의 체크리스트

- [x] 장소 20개의 필드 구조 확정 (`id` `area` `stayMinutes` `travelMinutes` `tags` 추가)
- [x] 필터를 총 소요 시간(체류 + 이동) 기준으로 정리
- [x] 하드코딩 Match 퍼센트 삭제
- [x] Loading·Empty·Error 세 가지 상태 화면 구분
- [x] 모바일 375px 점검
- [x] Week 2 API 요청·응답 형식 문서화
- [x] 학습 기록의 React 예제를 실제 vanilla JS 코드로 교체

### 공부한 것

- **필드 이름은 값의 뜻과 맞아야 한다.** `distance`라는 이름에 "분" 단위 값이 들어 있었고, 카드는 `78분`과 `예시 이동 시간 13분`을 나란히 보여줬다. 사용자는 이걸 78 + 13 = 91분으로 읽는다. 필터 계산 자체는 틀리지 않았지만, 이름이 애매하면 화면도 애매해진다.
- **State는 React에만 있는 개념이 아니다.** `index.html`에서는 입력칸 자체(`.value`)가 값을 기억한다. 대신 화면을 다시 그리는 일은 내가 `innerHTML`로 직접 해야 한다.
- **정렬 기준이 곧 제품의 주장이다.** 총 소요 시간이 짧은 순으로 정렬하면, 90분이 비어 있어도 20분짜리 코스를 먼저 추천한다. "남는 시간을 나만의 우회로로"라는 제품 전제와 어긋난다.
- **한국어 줄바꿈**은 `word-break: keep-all`이 필요하다. 없으면 모바일에서 "우회로 / 로."처럼 단어 중간이 잘린다.

### 구현한 것

- `places` 20개를 새 구조로 다시 작성했다. `minutes` → `stayMinutes` + `travelMinutes`로 분리하고, `id` `area` `tags`를 추가했다. 총 소요 시간은 이전과 같게 유지했다.
- 카드가 `총 48분 · 7,000원` / `이동 7분 + 머무는 시간 41분 · 남은 60분 중 12분 여유`를 보여준다.
- `92 - index * 7`로 계산되던 가짜 Match 퍼센트를 삭제했다. 입력 조건과 아무 상관 없는 숫자를 "% Match"로 보여주는 것은 "설명 가능한 추천"이라는 이 제품의 정체성과 맞지 않는다.
- 정렬을 총 소요 시간 내림차순(= 남은 시간을 알차게 쓰는 순)으로 바꿨다.
- Loading(찾는 중), Empty(조건에 맞는 코스 없음), Error(입력을 고쳐야 함) 세 상태를 색과 문구로 구분했다. Loading은 Week 2에 `fetch()`가 들어갈 자리를 미리 만들어 둔 것이다.
- 도착지 조사 처리를 추가했다. `성수역로` → `성수역으로`, `서울숲로` → `서울숲으로`.
- `docs/WEEK2_API_CONTRACT.md`를 새로 썼다.

### 고민과 선택

- **오늘 API를 넣을까?** 넣지 않기로 했다. 이유는 세 가지다. (1) REST key를 `index.html`에 적으면 페이지 소스 보기만으로 노출된다. (2) 카카오 로컬 REST API는 브라우저에서 직접 부르면 CORS로 막히는 경우가 많아 결국 서버가 필요하고, 그게 Week 2다. (3) API를 붙여도 그 위의 추천 로직이 틀려 있으면 데이터만 진짜가 된다. 로직을 먼저 맞추고 데이터를 갈아끼우는 순서가 안전하다.
  - 대신 `docs/WEEK2_API_CONTRACT.md`에 요청·응답 형식을 확정해서, 다음 주에 FastAPI만 얹으면 되게 했다. 응답 필드 이름을 `index.html`의 `places`와 똑같이 맞췄기 때문에 카드 렌더링 코드는 바꾸지 않아도 된다.
- **정렬을 "시간을 알차게 쓰는 순"으로 바꾼 것의 위험**: 가장 잘 맞는 코스가 여유를 12분만 남긴다. 실제 약속이라면 빠듯하게 느낄 수 있다. 지금은 여유 분을 카드에 그대로 표시해서 사용자가 판단하게 두었다. Week 4에서 점수를 만들 때 "버퍼가 너무 적으면 감점"을 가중치로 넣을지 검토한다.
- **`index.html`과 `frontend/`가 달라지는 문제**: 의도한 것이다. `frontend/`는 Day 2에 만든 Next.js 실험본이고 이번 주 제출 범위가 아니다. 두 파일을 지금 동기화하면 규칙이 다른 코드를 이중 관리하게 된다. 어느 쪽을 본선으로 삼을지는 Week 2를 시작할 때 한 번에 결정한다.
- **새 아이디어 분류** (`docs/MVP_DECISION_RULES.md` 기준): `tags` = 핵심(추천 이유의 재료), Loading 상태 = 핵심(Day 6 항목), `indoor`·`crowd` 필드 = 확장(넣지 않음), 정규화 기반 점수 = 보류(Week 4).

#### 다크 모드에서 글씨가 보이지 않음

  바뀌었다. Pico는 밝은 글씨 색을 골랐는데, 나는 **배경만** 크림색으로 덮어썼다.
  결과적으로 크림색 배경 위에 흰 글씨.
- **재현**: 브라우저를 다크 모드로 놓고 확인. `h1` 색이 `rgb(240,241,243)`,
  `body` 배경이 `rgb(246,242,233)`. 입력 카드까지 검은색이었다.
- **왜 놓쳤나**: 내 테스트 환경이 밝은 테마였다. 색을 지정한 요소(.eyebrow, .helper,
  .breakdown)는 멀쩡했고, **색을 지정하지 않고 Pico에 맡긴 요소만** 깨졌다.
  사용자가 말한 세 곳이 정확히 그 세 곳이었다.
- **해결**: `<html data-theme="light">`로 테마를 고정하고, `h1/h2/h3`와 `.intro`의
  색을 직접 지정.
- **배운 것**: CSS 프레임워크를 부분적으로만 덮어쓰면 위험하다. 배경을 바꿨으면
  글씨도 같이 책임져야 한다. 그리고 **내 화면에서 잘 보인다는 건 증거가 아니다.**

#### 고민과 선택

- **디자인을 옮기는 것과 React를 쓰는 것은 다른 문제다.** 마음에 든 것은
  강한 문구, 형광 연두, 랜딩 구조였는데 전부 HTML과 CSS다. React가 필요 없다.
- `index.html`을 본선으로 유지한다. 이미 배포돼 링크가 살아있고, Next.js로 갈아타면
  GitHub Pages가 그대로 받지 못해 배포를 처음부터 다시 해야 한다.
  남은 4주는 화면이 아니라 서버 작업이 대부분이다.
- `frontend/`는 지우지 않고 둔다. 지워서 얻는 게 없다.

#### 막힌 점과 해결 과정

- **한글에서 히어로 제목 두 줄이 겹쳤다.** 원본 CSS가 `line-height: 0.86`,

  위아래 줄이 붙는다. `line-height: 1.05`, `letter-spacing: -0.045em`으로 풀었다.
- 배운 것: 영문 디자인 시안을 한글에 그대로 쓰면 자간·행간에서 깨진다.

## 7 · FastAPI 서버와 브라우저 연결

### 진행 방식을 바꿨다

이 구간은 내가 코드를 받아 적고 Claude가 설명하는 방식으로 진행했다.
`PLAN.md`의 "★ 한 군데는 직접"을 아예 전부 직접 친 셈이다.
주석도 내 말로 다시 달았다.

### 구현한 것

- `backend/`에 Python 3.12 가상환경, FastAPI 설치
- `/health` — 서버가 살아있는지
- `/places` — 장소 20개 전부
- `/recommend` — 조건에 맞는 후보 2개 (POST)
- 장소 20개를 `index.html`에서 `backend/data/places.json`으로 분리
- `index.html`에 `askServer()` 추가 — 서버에 물어보고, 실패하면 `null`

### 공부한 것

- **`@app.get("/health")`은 `addEventListener`와 같은 구조다.** 브라우저에서는
  "버튼을 누르면", 서버에서는 "이 주소로 오면" 함수를 실행한다.
- **Pydantic은 `if` 검사를 대신해준다.** `time: int`라고 선언한 것만으로
  `time`에 글자가 오면 422와 함께 이유를 알려준다. 코드를 한 줄도 안 썼다.
- **GET과 POST의 차이.** GET은 "보여줘", POST는 "이 정보로 처리해줘".
  조건 5개를 보내야 하니 추천은 POST가 맞다.
- **CORS와 preflight.** 브라우저는 진짜 요청 전에 `OPTIONS`로 "POST 보내도 돼요?"를
  먼저 묻는다. 서버가 허락해야 진짜 요청을 보낸다.
- **`async`와 `await`.** 서버 응답은 시간이 걸리므로 기다려야 한다.
  `await`를 쓰려면 함수에 `async`가 붙어야 한다.
- **파이썬과 자바스크립트의 들여쓰기 차이.** 파이썬은 들여쓰기로 코드 구조를 판단해서
  틀리면 아예 안 돌아간다. 자바스크립트는 `{ }`로 판단해 틀려도 돌아간다.

### 막힌 점과 해결 과정

#### 오타 두 개 — 성격이 완전히 달랐다

```python
nd place["cost"] <= req.budget      # and 에서 a 빠짐
activitiy: str                       # activity 오타, 두 군데 모두
```

첫 번째는 파이썬이 줄 번호와 화살표까지 찍어서 알려줬다. 실행조차 안 된다.
두 번째는 **두 군데 다 똑같이 틀려서 파이썬이 아무 불평도 안 했다.** 문법적으로 완벽하니까.

그런데 `docs/WEEK2_API_CONTRACT.md`는 `activity`로 정해뒀고 `index.html`도 그렇게 보낸다.
나중에 연결할 때 422로 터졌을 것이다.

> 컴퓨터가 잡아주는 오류가 오히려 착한 오류다. 조용히 넘어가는 게 무섭다.

#### 브라우저가 서버를 못 불렀는데, 화면은 멀쩡했다

CORS를 열었는데도 서버 로그에 `OPTIONS`만 찍히고 `POST`가 없었다.
그런데 화면에는 카드 2개가 정상으로 떠 있었다.

**대비책이 조용히 작동한 것이었다.** 서버가 실패하자 내장 20개로 계산해서
겉보기에는 성공과 구별되지 않았다. 서버 로그의 POST 건수를 세고서야 알았다.

원인은 `file://`이었다. 그렇게 열면 브라우저가 페이지에 출처 `null`을 부여하고
네트워크 요청을 막는다. `python -m http.server 5500`으로 띄우니 바로 됐다.

> **화면이 멀쩡하다고 연결이 된 것은 아니다.** 대비책이 잘 만들어져 있을수록
> 실패가 눈에 안 보인다. 로그를 봐야 한다.

  카카오와 무관하다. 키가 필요한 건 `/geocode` 하나뿐이다.
  의존하지 않는 부분을 먼저 만들어 진도를 이어갔다.
- **서버가 없어도 화면이 동작하게 만들었다.** 이렇게 하지 않으면 배포된 사이트가
  당장 깨진다. 서버는 내 노트북에만 있기 때문이다.
  Figma 화면 07(서버 오류)이 다루려던 상황이 정확히 이것이다.
- **`allow_origins=["*"]`는 개발용이다.** 서버를 배포할 때 실제 도메인으로 좁힌다.
  코드에 주석으로 남겨뒀다.
